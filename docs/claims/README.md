# 작업 클레임 (병렬 워커용 lock)

여러 워커가 동시에 돌기 때문에 **작업 단위로 선점**한다. (aaaw `docs/claims/README.md` 규약 그대로 이식)

- 파일명: `<작업ID>.lock` (예: `T2.lock`) — 작업ID = `docs/PROGRESS.md` 표의 ID.
- **한 번호는 한 작업만 가리킨다.** 신규 작업은 «이미 쓰인 번호 중 가장 큰 것 +1», 번호 재사용 금지.
  - **번호는 눈으로 찾지 말고 `python3 tools/task_state.py --new-id` 로 뽑는다.** 그 자는 **표와 커밋 이력 중 큰 쪽**에서 +1 한다.
    ⚠ **«표에서 가장 큰 것» 만 보면 안 된다 — 표는 줄어들 수 있다.** 누가 작업을 접으며 행을 지우면 최대가 **내려가고**
    다음 사람이 규칙을 그대로 따르다 **같은 번호를 다시 뽑는다**. 2026-09-10 에 실제로 났다: T409(라이선스)를 접으며
    행을 지워 최대가 409 → 408 이 됐고 30분 뒤 다른 워커가 **다시 409** 를 발급했다(결정 1180 ⑥ · T415).
    커밋 제목은 append-only 라 안 줄어든다 — 그래서 발급은 거기서 뽑는다.
  - **작업을 접을 때 행을 지우지 않는다 — `✂` 로 남겨 번호를 태운다**(T284·T296 이 그 꼴). 지우면 그 번호가 되살아난다.
    `task_state.py --check` 가 «이력에는 있는데 표에 행이 없는 번호» 를 **알리기만** 한다(rc 는 안 건드린다).
  - ⚠ 이 자는 **같은 순간 둘이 같은 번호를 뽑는 갈래는 못 막는다**(둘 다 같은 답을 얻는다 · 2026-09-10 T414 가 그랬다).
    그것을 가르는 것은 아래 **push 순서**다 — 늦게 민 쪽이 제 번호를 옮긴다.
- 내용 1줄: `<UTC ISO8601> <SID>` 예) `2026-09-06T01:30:11Z sess-0630-8412`
- 선점 절차: **① `docs/PROGRESS.md` 표에서 그 작업의 «상태» 칸을 읽는다 — ⬜ 가 아니면 잡지 않는다** →
  ② lock 파일 생성 → 커밋 → **push. push 가 먼저 성공한 쪽이 이긴다.**
  push 충돌 시 `git fetch && git rebase origin/main` 후 자기 lock 이 살아있는지 확인 —
  사라졌거나 남의 lock 이 있으면 포기하고 다음 작업으로.
  ⚠ **①이 없으면 «lock 이 없다» 를 «할 일이 남았다» 로 읽게 된다.** 임자가 **일을 끝내고 lock 을 반납한 직후**에는
  `claims/` 가 비어 있어 오히려 «아무도 안 잡았다» 로 보인다 — 2026-09-09 하루에 이 꼴이 세 번 났다
  (T296 은 한 시간 전에 T295 로 이미 등재돼 있었고 · T349·T344 는 잡으려는 순간 이미 끝나 있었다 · 결정 846·973).
  ⬜ 가 아니면 그것이 무슨 뜻인지도 정해져 있다: **✅ = 끝난 것 · 🔄 = 임자가 하고 있거나 방금 반납한 것** — 어느 쪽도 «내가 지금 시작할 일» 이 아니다.
- **90분 지난 lock 은 죽은 것으로 보고 뺏는다** (뺏을 때 기존 파일을 자기 SID 로 덮어 커밋·push).
  장기 세션은 90분 전에 타임스탬프를 갱신해 push 한다.
- 작업이 끝나거나 중단되면 성공·실패 무관 **반드시 삭제**한다.

## ⚠ «직전 슬롯 세션의 lock» 도 남의 lock 이다

**같은 워커 문자(A~P·Q)라도 SID 가 다르면 다른 세션이고, 그 lock 은 90분 규약을 그대로 적용한다.**
«앞 세션이 등재만 하고 끝났겠지» 라는 추정으로 인계하지 말 것 — 앞 세션은 자주 아직 살아 있다
(aaaw 에서 이 추정으로 한 시간짜리 작업이 통째로 버려진 실사고가 2건 있었다).

- ⓐ 시각을 계산해 **90분이 실제로 지났는지** 확인한다(lock 파일의 타임스탬프 ↔ `date -u`).
- ⓑ 90분 전이면 그 작업은 **건드리지 않고** 다른 작업을 잡거나, 열린 작업이 그것뿐이면 **아무것도 안 하고 물러난다**.
- ⓒ 장기 작업 중인 세션은 규약대로 90분 전에 타임스탬프를 갱신해 push 한다 — 그것이 «살아 있다» 는 유일한 신호다.

## 이 레포만의 추가 규약

- 한 작업이 만지는 파일 범위는 PROGRESS 표의 «범위» 열에 적힌 폴더다. 두 작업이 같은 파일을 만져야 하면 뒤 번호가 기다린다.
- `Assets/StreamingAssets/data/*.json` 은 어느 작업도 손으로 고치지 않는다 — `tools/check_data_sync.sh --sync` 로만 갱신한다.
